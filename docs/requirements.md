# PathTrip 기능 요구사항

> 이 문서는 PathTrip 서비스의 기능 요구사항을 정의한다.
> 본 문서를 기준으로 API 명세, ERD 설계, 백엔드 구현을 진행한다.

---

## 1. 문서 목적

이 문서는 PathTrip 서비스가 제공해야 하는 기능과 각 기능의 동작 조건을 정의한다.

본 문서를 통해 다음을 명확히 한다.

* 어떤 기능을 구현할 것인가
* 사용자는 어떤 흐름으로 기능을 사용하는가
* 기능을 사용하기 위해 어떤 입력값이 필요한가
* 서버는 어떤 조건을 검증해야 하는가
* 성공 시 어떤 결과를 반환해야 하는가
* 실패 시 어떤 예외 상황이 발생할 수 있는가
* MVP에 포함할 기능과 추후 개발 기능은 무엇인가

---

## 2. 서비스 개요

PathTrip은 사용자가 여행 중 방문하고 싶은 장소, 맛집, 카페, 숙소 등을 입력하면 위치 정보와 이동 시간을 기반으로 효율적인 여행 동선을 자동 추천하는 서비스다.

사용자는 단순히 장소를 저장하는 것이 아니라, 여러 장소를 어떤 순서로 방문해야 이동 시간을 줄이고 더 효율적으로 여행할 수 있는지 추천받을 수 있다.

---

## 3. 서비스 기획 배경

여행을 준비할 때 사용자는 가고 싶은 장소를 많이 저장하지만, 실제로 어떤 순서로 이동해야 효율적인지 판단하기 어렵다.

예를 들어 제주도 2박 3일 여행을 계획할 때 맛집, 카페, 관광지, 사진 스팟을 많이 저장해두더라도 직접 동선을 짜는 과정에서 다음과 같은 문제가 발생한다.

* 장소 간 거리를 직접 확인해야 한다.
* 이동 시간이 비효율적으로 낭비될 수 있다.
* 같은 지역의 장소를 효율적으로 묶기 어렵다.
* 맛집 중심, 관광 중심 등 여행 목적을 반영하기 어렵다.
* 일정 계획에 많은 시간이 소요된다.

PathTrip은 이러한 문제를 해결하기 위해 위치, 이동 시간, 장소 카테고리, 사용자 우선순위를 기반으로 여행 동선을 자동 생성한다.

---

## 4. 핵심 목표

* 사용자가 여행 계획을 쉽게 세울 수 있어야 한다.
* 이동 시간을 최소화할 수 있어야 한다.
* 사용자가 입력한 장소를 효율적인 순서로 정렬할 수 있어야 한다.
* 맛집, 카페, 관광지 등 여행 목적을 반영할 수 있어야 한다.
* 추천된 동선을 저장하고 다시 조회할 수 있어야 한다.
* 향후 사용자 추천 동선, 리뷰, AI 추천 기능으로 확장할 수 있어야 한다.

## 5. 사용자 유형

### 5.1 비회원

비회원은 서비스를 탐색할 수 있으나, 개인 여행 일정 생성과 동선 추천 기능은 사용할 수 없다.

가능한 기능:

* 회원가입
* 로그인

제한되는 기능:

* 여행 생성
* 장소 추가
* 자동 동선 추천
* 추천 동선 저장

---

### 5.2 회원

회원은 로그인 후 자신의 여행 일정을 생성하고 장소를 추가하며 자동 동선 추천을 받을 수 있다.

가능한 기능:

* 내 정보 조회
* 여행 생성, 조회, 수정, 삭제
* 여행에 장소 추가
* 장소 목록 조회, 수정, 삭제
* 자동 동선 추천
* 추천 동선 저장 및 조회

---

### 5.3 주요 대상 사용자

PathTrip의 주요 대상 사용자는 다음과 같다.

* 여행 동선을 짜기 어려운 사용자
* 이동 시간을 고려한 여행 계획이 필요한 사용자
* 맛집, 관광지, 카페를 효율적으로 묶고 싶은 사용자
* 짧은 여행 기간 안에 많은 장소를 방문하고 싶은 사용자
* 여행 계획에 드는 시간을 줄이고 싶은 사용자

## 6. 공통 정책

### 6.1 인증 정책

* 여행, 장소, 동선 추천 기능은 로그인한 사용자만 사용할 수 있다.
* 인증 방식은 JWT Bearer Token을 사용한다.
* 인증이 필요한 API는 Access Token을 요구한다.

---

### 6.2 권한 정책

* 사용자는 자신이 생성한 여행만 조회, 수정, 삭제할 수 있다.
* 사용자는 자신의 여행에 포함된 장소만 수정, 삭제할 수 있다.
* 사용자는 자신의 여행에 대한 추천 동선만 조회할 수 있다.
* 다른 사용자의 비공개 여행 정보에는 접근할 수 없다.

---

### 6.3 삭제 정책

* 중요 데이터는 soft delete를 우선 고려한다.
* 삭제된 데이터는 기본 조회 결과에 포함하지 않는다.
* 실제 물리 삭제가 필요한 경우는 별도 정책을 따른다.

---

### 6.4 시간 정책

* DB에는 UTC 기준으로 시간을 저장한다.
* API 응답은 ISO 8601 형식의 날짜 문자열을 사용한다.
* 클라이언트는 필요 시 Asia/Seoul 기준으로 표시한다.

---

### 6.5 응답 정책

성공 응답은 다음 형식을 따른다.

```json
{
  "success": true,
  "data": {}
}
```

실패 응답은 다음 형식을 따른다.

```json
{
  "success": false,
  "code": "ERROR_CODE",
  "message": "에러 메시지"
}
```

## 8. Auth 요구사항

---

### Auth-001. 회원가입

#### 기능 설명

사용자는 이메일, 비밀번호, 닉네임을 입력하여 회원가입할 수 있다.

#### 사용자 시나리오

1. 사용자가 이메일, 비밀번호, 닉네임을 입력한다.
2. 서버는 입력값을 검증한다.
3. 서버는 이메일 중복 여부를 확인한다.
4. 비밀번호를 해싱하여 저장한다.
5. 사용자 계정을 생성한다.

#### 입력값

| 필드       | 타입     | 필수 | 설명       |
| -------- | ------ | -- | -------- |
| email    | string | Y  | 사용자 이메일  |
| password | string | Y  | 사용자 비밀번호 |
| nickname | string | Y  | 사용자 닉네임  |

#### 처리 조건

* 이메일은 올바른 이메일 형식이어야 한다.
* 비밀번호는 최소 8자 이상이어야 한다.
* 이미 가입된 이메일은 사용할 수 없다.
* 비밀번호는 bcrypt로 해싱하여 저장한다.

#### 성공 결과

* 사용자 계정이 생성된다.
* 생성된 사용자 정보를 반환한다.
* 비밀번호는 응답에 포함하지 않는다.

#### 예외 상황

| 상황          | 에러 코드                |
| ----------- | -------------------- |
| 이메일 형식 오류   | INVALID_INPUT        |
| 비밀번호 조건 불만족 | INVALID_INPUT        |
| 이메일 중복      | EMAIL_ALREADY_EXISTS |

#### 우선순위

MVP

---

### Auth-002. 로그인

#### 기능 설명

사용자는 이메일과 비밀번호로 로그인할 수 있다.

#### 사용자 시나리오

1. 사용자가 이메일과 비밀번호를 입력한다.
2. 서버는 이메일로 사용자를 조회한다.
3. 서버는 비밀번호를 비교한다.
4. 로그인 성공 시 Access Token을 발급한다.

#### 입력값

| 필드       | 타입     | 필수 | 설명       |
| -------- | ------ | -- | -------- |
| email    | string | Y  | 사용자 이메일  |
| password | string | Y  | 사용자 비밀번호 |

#### 처리 조건

* 이메일과 비밀번호가 일치해야 한다.
* 비밀번호는 bcrypt compare로 검증한다.
* 로그인 성공 시 JWT Access Token을 발급한다.

#### 성공 결과

* Access Token을 반환한다.
* 사용자 기본 정보를 반환한다.

#### 예외 상황

| 상황              | 에러 코드               |
| --------------- | ------------------- |
| 입력값 누락          | INVALID_INPUT       |
| 이메일 또는 비밀번호 불일치 | INVALID_CREDENTIALS |

#### 우선순위

MVP

* 사용자 ID, 이메일, 닉네임을 반환한다.

## 10. Trips 요구사항

---

### Trip-001. 여행 생성

#### 기능 설명

로그인한 사용자는 여행 제목, 지역, 시작일, 종료일을 입력하여 여행 일정을 생성할 수 있다.

#### 사용자 시나리오

1. 사용자가 여행 제목, 지역, 시작일, 종료일을 입력한다.
2. 서버는 인증 여부를 확인한다.
3. 서버는 날짜 범위를 검증한다.
4. 서버는 현재 사용자 소유의 여행을 생성한다.

#### 입력값

| 필드        | 타입     | 필수 | 설명     |
| --------- | ------ | -- | ------ |
| title     | string | Y  | 여행 제목  |
| region    | string | Y  | 여행 지역  |
| startDate | string | Y  | 여행 시작일 |
| endDate   | string | Y  | 여행 종료일 |

#### 처리 조건

* 로그인한 사용자만 여행을 생성할 수 있다.
* title은 비어 있을 수 없다.
* startDate는 endDate보다 늦을 수 없다.
* 생성된 여행은 현재 사용자에게 귀속된다.

#### 성공 결과

* 여행 일정이 생성된다.
* 생성된 여행 ID를 반환한다.

#### 예외 상황

| 상황          | 에러 코드              |
| ----------- | ------------------ |
| 인증되지 않은 사용자 | UNAUTHORIZED       |
| 필수값 누락      | INVALID_INPUT      |
| 날짜 범위 오류    | INVALID_DATE_RANGE |

#### 우선순위

MVP

### Trip-002. 여행 목록 조회

#### 기능 설명

로그인한 사용자는 자신이 생성한 여행 목록을 조회할 수 있다.

#### 사용자 시나리오

1. 사용자가 여행 목록 조회를 요청한다.
2. 서버는 인증 여부를 확인한다.
3. 현재 사용자가 생성한 여행 목록을 조회한다.
4. 삭제되지 않은 여행만 반환한다.

#### 입력값

| 필드    | 타입     | 필수 | 설명     |
| ----- | ------ | -- | ------ |
| page  | number | N  | 페이지 번호 |
| limit | number | N  | 페이지 크기 |

#### 처리 조건

* 로그인한 사용자만 조회할 수 있다.
* 자신의 여행만 조회된다.
* 삭제된 여행은 조회되지 않는다.

#### 성공 결과

* 여행 목록을 반환한다.
* 페이지네이션 정보를 포함한다.

#### 예외 상황

| 상황          | 에러 코드        |
| ----------- | ------------ |
| 인증되지 않은 사용자 | UNAUTHORIZED |

#### 우선순위

MVP

#### 기능 설명

#### 입력값

### Route-001. 자동 동선 추천

#### 기능 설명

사용자가 여행에 추가한 장소들을 기반으로 이동 시간이 짧고 효율적인 추천 동선을 생성한다.

#### 사용자 시나리오

1. 사용자가 여행에 여러 장소를 추가한다.
2. 사용자가 자동 동선 추천을 요청한다.
3. 서버는 여행과 장소 목록을 조회한다.
4. 서버는 장소 간 이동 시간 또는 거리를 계산한다.
5. 서버는 효율적인 방문 순서를 생성한다.
6. 추천 동선을 반환한다.

#### 입력값

| 필드               | 타입     | 필수 | 설명     |
| ---------------- | ------ | -- | ------ |
| tripId           | number | Y  | 여행 ID  |
| startTime        | string | N  | 출발 시간  |
| transportType    | string | N  | 이동 수단  |
| optimizationType | string | N  | 최적화 기준 |

#### 처리 조건

* 로그인한 사용자만 추천받을 수 있다.
* 해당 여행이 존재해야 한다.
* 해당 여행이 현재 사용자의 여행이어야 한다.
* 장소가 최소 2개 이상 있어야 한다.
* 각 장소는 latitude, longitude를 가지고 있어야 한다.
* MVP에서는 규칙 기반 추천 알고리즘을 사용한다.

#### 성공 결과

* 추천 방문 순서를 반환한다.
* 총 이동 시간과 총 이동 거리를 반환한다.
* 장소별 예상 방문 순서를 반환한다.

#### 예외 상황

| 상황          | 에러 코드                     |
| ----------- | ------------------------- |
| 인증되지 않은 사용자 | UNAUTHORIZED              |
| 여행 없음       | TRIP_NOT_FOUND            |
| 권한 없음       | FORBIDDEN                 |
| 장소 부족       | NOT_ENOUGH_PLACES         |
| 좌표 없는 장소 존재 | PLACE_COORDINATE_REQUIRED |
| 지도 API 실패   | MAP_API_ERROR             |

## 14. 추후 개발 기능

### 14.1 방문 인증 기반 리뷰 시스템

사용자는 실제 방문한 장소에 대해 맛, 분위기, 서비스, 재방문 의사 등을 평가할 수 있다.

방문 인증 리뷰는 일반 리뷰보다 높은 신뢰도를 가진다.

---

### 14.2 매장 문의 기능

사용자는 매장에 영업시간, 대기 현황, 주차 가능 여부 등을 문의할 수 있다.

초기에는 실시간 채팅이 아닌 문의/답변 방식으로 구현한다.

---

### 14.3 사용자 추천 동선 공유 기능

사용자는 자신이 직접 만든 여행 동선을 공개할 수 있다.

다른 사용자는 공개된 동선을 조회, 저장, 좋아요 할 수 있다.

---

### 14.4 크리에이터 기반 여행 코스 기능

인플루언서나 크리에이터는 자신이 추천하는 맛집, 카페, 명소 기반 여행 코스를 생성하고 공유할 수 있다.

다른 사용자는 해당 크리에이터를 팔로우하고 추천 동선을 확인할 수 있다.

---

### 14.5 유저 검증 동선 추천 기능

자동 추천 동선 외에도 실제 유저가 효율적으로 구성한 동선을 추천받을 수 있다.

이를 통해 자동 추천 알고리즘의 한계를 보완한다.

---

### 14.6 Redis 캐싱

반복적인 장소 검색과 좌표 변환 요청에 대해 Redis 캐싱을 적용한다.

이를 통해 외부 지도 API 호출 횟수를 줄이고 응답 속도를 개선한다.

---

### 14.7 AI 기반 추천

사용자의 여행 목적과 취향을 자연어로 입력받아 LLM이 여행 성향을 분석한다.

예시:

* 맛집 중심 여행
* 카페 중심 여행
* 사진 스팟 중심 여행
* 관광 중심 여행

분석 결과를 동선 추천 정책에 반영한다.

---
